Hi all，

最近在处理一个case时了解到了一些ER相关的特性，总结如下： http://intra.21vbluecloud.com/sites/Azure/WATS/Shared%20Documents/WATS_KB_Training%20-%20Linked%20Files/bbb%202.cap

客户的环境是标准的ER专线配置，需求是从本地server172.30.2.98访问AzureVM 173.20.11.102

双方正常通信时，在VM的node上和ERgateway的两个instance上抓包，都只能看到172.30.2.98发往173.20.11.102的包，但无法看到回包

而客户本地的server其实是能正常收到AzureVM的回包的。

于是我们请NW的同事在MSEE上做了抓包，能看到有正常的回包

经排查，在NODE的抓包中看到有如下的UDP包：

其中，139.219.131.116是ER GATEWAY的IP，10.203.128.1和10.203.128.2是MSEE的IP，也就是说NODE把自己伪装成了ER gateway在给MSEE回包。

我们可以右键点下这种包，然后选Decode As，在弹出的框中的current里选择vxlan，点确定

然后Wireshark就会对包进行解码，解出来的包正是AzureVM给本地Server的回包（需要wireshark版本在2.0以上）

总结一下，ER的通信，本地发往Azure的包是经过On-Premise→ MSEE→ER Gateway→Node→Instance的次序传递的。

但Azure发往本地的包则是Instance→Node→MSEE→On-premise，并不经过ER gateway

在Node将包发往MSEE前，会打上如下的vxlan header，以将包伪装成是由ER Gateway发出

Encap Type: VXLAN

Encap Destination(s) :

{ Src IP address=139.219.131.116, Dest IP address=10.203.128.1, MAC address=00-00-00-00-00-00, GRE key=4147 }

{ Src IP address=139.219.131.116, Dest IP address=10.203.128.2, MAC address=00-00-00-00-00-00, GRE key=4147 }

所以以后我们在ER上抓包时，从Azure发往本地的包要在VM的node上或MSEE上去抓。
