工单: SR_20250728365312 _ 在做备份还原后，无法用域账号通过RDP登录，报错为network password incorrect

发生脱域的原因:

计算机账户密码不匹配与时间偏差

1,  Active Directory 计算机账户密码机制：

当一台计算机（无论是物理机还是虚拟机）加入 Active Directory 域时，它会在域中创建一个唯一的计算机账户（通常以计算机名后跟 $ 表示，如 MyServer$）。

与用户账户类似，计算机账户也有一个密码。这个密码由操作系统自动管理，默认情况下每 30 天自动更改一次。

这个密码用于在计算机启动、访问域资源（如文件共享、应用服务器）以及与其他域计算机通信时，向域控制器进行相互身份验证。

关键点：计算机账户密码必须同时存储在：

本地计算机的安全账户管理器（SAM）数据库或 LSA 机密中。

Active Directory 域控制器上的对应计算机账户对象中。

这两个地方存储的密码必须完全一致，身份验证才能成功。

2,  Azure 备份还原：

Azure 备份（使用 VM 扩展和 VSS）捕获的是虚拟机在备份时间点的磁盘状态（操作系统盘和数据盘）

还原操作是将虚拟机回滚到这个过去的时间点的磁盘状态。这包括：

à操作系统文件

à注册表设置

à本地 SAM 数据库 / LSA 机密（其中包含当时的计算机账户密码）

à系统时间（在启动时会尝试同步，但初始启动时可能基于还原点的时间）

3,  如果在还原点之后计算机账户密码已更改，当还原的虚拟机启动并尝试联系域控制器进行身份验证（例如，用户登录、系统服务启动、访问网络资源）时会导致密码不匹配，身份验证失败

由于无法通过域控制器的身份验证，域控制器认为该计算机“不可信”。操作系统（如 Windows）会检测到这种失败，并报告“信任关系失败”或类似错误（例如 “The trust relationship between this workstation and the primary domain failed”）

4, Kerberos（Windows 域身份验证的核心协议）对时间同步极其敏感。通常要求计算机与域控制器之间的时间差不超过 5 分钟。

还原的虚拟机在启动时，其系统时间可能被设置为接近备份时间点 T0 的时间（尤其是在未配置或无法立即联系时间源的情况下）。而域控制器的时间是当前的 T_now。

如果 T_now - T0 > 5 分钟（这在还原旧备份时非常常见），即使密码匹配，Kerberos 认证也会因为时间偏差过大而失败，进一步加剧了“信任关系失败”的问题

Azure 备份还原加域虚拟机导致域关系破坏的核心并非备份还原技术本身的缺陷，而是 Active Directory 安全机制（计算机账户密码轮换）与将系统状态回滚到过去时间点这一操作之间固有的冲突
