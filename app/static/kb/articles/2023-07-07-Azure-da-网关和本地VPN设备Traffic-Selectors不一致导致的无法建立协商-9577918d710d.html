问题现象：VPN连接中断后，无法再次建立协商

问题原因：由于Azure VPN 网关和本地VPN设备Traffic Selectors设置不一致导致的

排查分析:

本地与azure vpn连接中断后，重新协商无法通过，两侧报错日志相同均为 “IPSEC_SEND_TS_MISMATCH”。

“Azure VPN 网关Traffic Selectors 为TSI:0.0.0.0/0和TSR:0.0.0.0/0, 本地VPN设备Traffic Selectors为TSI:10.0.0.0/8和TSR:0.0.0.0/0”

Azure VPN 网关支持两种Traffic Selectors，分别为

1）TSI:0.0.0.0/0和TSR:0.0.0.0/0

2）All combinations of your on-premises network (local network gateway) prefixes to/from the Azure virtual network prefixes.例如本地地址空间为10.1.0.0/16 and 10.2.0.0/16, Azure 虚拟网络地址空间为192.168.0.0/16 and 172.16.0.0/16, 则Traffic Selectors 为

10.1.0.0/16 <====> 192.168.0.0/16

10.1.0.0/16 <====> 172.16.0.0/16

10.2.0.0/16 <====> 192.168.0.0/16

10.2.0.0/16 <====> 172.16.0.0/16

当前本地VPN设备Traffic Selectors 为TSI:10.0.0.0/8和TSR:0.0.0.0/0 与以上两种均不匹配。

当Azure VPN 网关协商创建QM Traffic Selectors TSI:0.0.0.0/0和TSR:0.0.0.0/0, 收到用户本地VPN 设备响应“Notify Message - Traffic Selectors Unacceptable”

当Azure VPN 网关使用第2种  Traffic Selectors on-premises network (local network gateway) prefixes to/from the Azure virtual network prefixes 发送协商消息，收到本地VPN设备响应消息“Notify Message - No Additional SAs”

当本地VPN设备主动发起Traffic Selector协商（TSI:10.0.0.0/8和TSR:0.0.0.0/0”），Azure VPN 网关接受协商请求协商成功。

此工单中客户无法通过本地设备重置连接，因此通过Azure Portal 重置Azure VPN触发主备实例切换，在此过程中重新触发IKE/IPsec 协商，当本地VPN设备主动发起Traffic Selector协商时会重新建立IPsec 隧道成功。

综合以上分析该问题是由于Azure VPN 网关和本地VPN设备Traffic Selectors设置不一致导致的。因此建议咨询Juniper 工程师尝试修改本地与Azure VPN IPsec 连接Traffic Selectors 设备。
