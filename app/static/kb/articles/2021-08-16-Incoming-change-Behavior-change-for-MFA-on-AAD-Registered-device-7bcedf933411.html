问题现象 / 场景

  • We have an incoming feature behavior change for AAD device registration with MFA.

背景信息

  • We have an incoming feature behavior change for AAD device registration with MFA.
  • How users are impacted:
  • To mitigate a recent found risk, users will be required to complete MFA once more before accessing an MFA protected resource in Azure AD, even if they have already performed MFA during device registration.
  • Impacted Scenario:
  • Users using AAD registered device, who were required to complete MFA during the device registration.
  • NOT impacted scenarios:
  • Users using non-registered devices
  • Users who sign into devices registered by someone else
  • Users who registered devices without MFA
  • Users who signed into system-registered devices (e.g. Hybrid Azure AD Joined)
  • Find deviceOwnership attribute, and \”mfa\” in deviceSystemMetadata -> RegistrationAuthMethods key.
  • Note that this sample is an AAD joined device, not exactly match with our scenario.
  • Customer ready content in Chinese:
  • 以下情形不受此更改的影响：
  • • 用户使用未注册设备
  • • 用户登录他人注册的设备
  • • 用户在注册设备过程时未被要求完成 MFA
  • • 用户登陆到系统注册设备（例如混合加入 Azure AD 的设备）

排查思路

  • Troubleshooting steps:
  • In evoSTS (Jarvis AadEvoSTSCHINA -> PerRequestTableIfx), search the correlationId of the unexpected MFA prompt, get deviceId of the authN request.
  • Check ASC tenant explorer and find the device with deviceId.
  • If the UserPrincipalObjectID in evoSTS equals deviceOwnership in ASC, and \”mfa\” exists in deviceSystemMetadata -> RegistrationAuthMethods key, the user is most likely to be impacted by this change.

原始内容清洗稿（保留备查）

We have an incoming feature behavior change for AAD device registration with MFA.

How users are impacted:

To mitigate a recent found risk, users will be required to complete MFA once more before accessing an MFA protected resource in Azure AD, even if they have already performed MFA during device registration.

Impacted Scenario:

Users using AAD registered device, who were required to complete MFA during the device registration.

NOT impacted scenarios:

Users using non-registered devices

Users who sign into devices registered by someone else

Users who registered devices without MFA

Users who signed into system-registered devices (e.g. Hybrid Azure AD Joined)

Troubleshooting steps:

In evoSTS (Jarvis AadEvoSTSCHINA -> PerRequestTableIfx), search the correlationId of the unexpected MFA prompt, get deviceId of the authN request.

Check ASC tenant explorer and find the device with deviceId.

Find deviceOwnership attribute, and \”mfa\” in deviceSystemMetadata -> RegistrationAuthMethods key.

If the UserPrincipalObjectID in evoSTS equals deviceOwnership in ASC, and \”mfa\” exists in deviceSystemMetadata -> RegistrationAuthMethods key, the user is most likely to be impacted by this change.

Sample: https://portal.microsoftgeneva.com/s/37D7C25E

Note that this sample is an AAD joined device, not exactly match with our scenario.

Customer ready content in Chinese:

感谢您为了设备注册后意外的 MFA 提示联系我们。为了提高 Azure AD 的基线安全性，我们正在更改在设备注册过程中进行多因素身份验证 （MFA） 的 Azure AD 行为。通过这一更改，我们不再接受在设备注册过程中完成的 MFA，而是要求用户在访问 Azure AD 中的 被MFA 保护的资源时再一次完成 MFA。此更改不会影响现有的 Azure AD 注册设备，直到其会话过期或失效；在会话过期后，当尝试从此设备访问被 Azure AD 保护的资源时，如果存在要求完成 MFA 的安全策略，用户将被要求完成 MFA。

以下情形不受此更改的影响：

• 用户使用未注册设备

• 用户登录他人注册的设备

• 用户在注册设备过程时未被要求完成 MFA

• 用户登陆到系统注册设备（例如混合加入 Azure AD 的设备）
