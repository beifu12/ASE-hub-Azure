RestoreOperationFailedV2

Error Code: RestoreOperationFailedV2

Error Message: Restore failed with an internal error.

The Restore operation fails because the replace disks operation is not supported for encrypted VMs.

How to verify if the failure is caused by this specific root cause?

Run the below Kusto query on the BCMBackupStats table and check if the TelemetryLogMessage contains "Exception in SwapDisksTask"

union cluster('mabprod1').database('MABKustoProd1').BCMRecoveryStats,

cluster('mabprodweu').database('MABKustoProd').BCMRecoveryStats,

cluster('mabprodwus').database('MABKustoProd').BCMRecoveryStats

|where TaskId = "<Task ID>"

|where TIMESTAMP > ago(1d)

|where TelemetryLogMessage contains "Exception in SwapDisksTask"

If the output contains Exception in SwapDisksTask message then this failure is because replace disks operation is not supported for encrypted VMs.

Workaround

Ask customer to try a different restore operation like ALR (Alternate location recovery) or restore backed-up disks .

Customer Ready Content

Restore operation failed because the replace disks operation is not supported for encrypted VMs, so we recommend you to try a different restore operation like restore the full virtual machine to the alternate location or restore backed-up disks .

Error code: CloudDosTimeboudLimitReached

Different Possible Restore Flows

We have different flows possible in Restore and backup. Internally ,we call it DiffTL flow

In Restore, DiffTL is enabled in one of these true

1.        any disk containing more than 4TB (at any point of the time)

2.        total number of disks is greater than 16

3.        Restored is triggered from unmanaged disk to managed

Flow of change observed by customer is as below

NonDiffTL route : Data transfer from vault > blob container created in staging storage account> VHD created in container > managed disk created in resource group

Symptom : One of the reasons for backup not getting triggered is Backup App being in disabled state. "Application '262044b1-e2ce-469f-a196-69ab7ada62d3'(Backup Management Service) is disabled."

Fix : If you see the above mentioned logs in the backup logs, then follow the steps below to re-enable the Backup app.

1.        In customer's subscription, navigate to "Azure active directory" and click on "Enterprise Application" and search for application id "262044b1-e2ce-469f-a196-69ab7ada62d3"

2.        In "Backup Management Service" app, set the "Enabled for users to sign-in" to Yes. Once done, trigger the backup, it should now not experience the above mentioned error.

UserErrorMigrationFromTrustedLaunchVmToNonTrustedTrustedVmNotAllowed

CSI incident for which this TSG is created - Incident-299662868 Details - IcM (microsofticm.com)

What is the symptom (error message, behavior) that customer see?

he VM Backup fails with "UserErrorMigrationFromTrustedLaunchVmToNonTrustedTrustedVmNotAllowed" for a non-Trusted VM.

How to verify the root cause of failure?

If a backup operation fails with "UserErrorMigrationFromTrustedLaunchVmToNonTrustedTrustedVmNotAllowed" and the following are true:

1.        The VM is a non-Trusted VM

2.        The VM name is the same as an earlier VM that was TVM (now deleted). The Resource Group must also be the same for both these VMs.

Recommended Steps for CSS

Due to a bug (linked below), a non-Trusted VM with the same name as an earlier TVM (now deleted) fails with "UserErrorMigrationFromTrustedLaunchVmToNonTrustedTrustedVmNotAllowed".

The bug item for tracking is: Bug 14090127: SecurityType in Container Info not updating - Boards (visualstudio.com)

Meanwhile, the following workaround solution can be discussed with the customer:

1.        Ask the customer to create a VM with a different name than that of the deleted TVM.

2.        The customer could create a VM with the same name, but in a different Resource Group to avoid this issue.
