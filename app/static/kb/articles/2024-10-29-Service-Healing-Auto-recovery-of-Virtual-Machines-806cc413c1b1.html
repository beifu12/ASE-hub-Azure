Fabric Service Healing

There is a component called Service Health Manager (SHM) within the Fabric Controller which is responsible for Service Healing. SHM constantly probes the nodes to check the health of the node.   When the SHM is not able to communicate with Host Agent the node will eventually move to Human Investigate. If there is a problem with the hardware of the node like for example if the disk goes bad and is out for replacement then that node will no longer be available for allocation and will marked as Out for Repair (OFR).

Currently the fault handing is only at the node level and not at the container level.

Human Investigate and Out for repair(OFR) are the only two states that are defined as terminal unhealthy which means someone has to manually recover these nodes.

Kusto Queries to detect/investigate Service Healing

To confirm Service Healing via Node:

cluster("azcsupfollower").database("AzureCM").ServiceHealingTriggerEtwTable

| where PreciseTimeStamp between(datetime({StartTime})..24h) and NodeId == "{NodeId}"

To understand if a tenant was service healed:

cluster("azcsupfollower").database("AzureCM").TMMgmtTenantEventsEtwTable

| where PreciseTimeStamp between(datetime({StartTime})..24h) and TenantName == "{TenantName}"

| project PreciseTimeStamp, TaskName, TenantName, Message

To understand tenant status for service healing:

cluster("azcsupfollower").database("AzureCM").ServiceHealingTenantStatusEtwTable

| project PreciseTimeStamp, State, Message

cluster("azcsupfollower").database("AzureCM").AzSMServiceHealingTriggerEvents

| where PreciseTimeStamp between(datetime({StartTime})..24h) and tenantName == "{TenantName}"

Delayed Service Healing

The physical node where the VMs are running may become unhealthy for a few different reasons. Azure monitors the node & detects unhealthy nodes, and attempts to recover the node is without impact to VMs. More information on this effort is posted :https://azure.microsoft.com/en-us/blog/improving-azure-virtual-machines-resiliency-with-project-tardigrade/ (Opens in new window or tab)

If the initial recovery attempt fails to recover the node, Azure collects additional detailed deep diagnostics telemetry understand and address such incidents.  Azure then proceeds to power cycle the node as a final step in the recovery attempt. If the node fails to return to healthy state even after power cycle, the node will be taken out of production for investigation. At this stage, the VMs are service healed to a healthy node. In this such a scenario, the total time taken for detection, initially recovery effort, collection of diagnostics data, and the power cycle, can delay service healing in this specific scenario.

Note: A delayed service healing could also be caused by a TOR failure, because then the communication between Host and Fabric could be impacted.
