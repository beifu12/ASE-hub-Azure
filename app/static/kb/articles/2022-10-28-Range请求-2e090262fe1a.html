一句话摘要

源站需要支持 Range 请求，否则会导致回源失败。

问题现象 / 场景

  • 源站需要支持 Range 请求，否则会导致回源失败。
  • SR_2019082848059_[S500]CDN无法缓存内容且向源地址发送重复请求
  • 默认开启了range回源功能，这时CDN节点会使用range0-0先请求一次源站来获取资源长度，随后按照一定的range范围进行分段请求，因此会出现客户端一次请求产生多次回源记录的现象，如果不需要的话，我们可以后端关闭range回源功能，如果源站的文件较小的话，这个不会有太大影响，如果文件较大的话，可能会影响回源成功率和回源带宽；
  • SR_2020071640119_[MS-LED]访问CDN加速域名时报错：This application has no explicit mapping for /error, so you are seeing this as a fallback.

SR_2019082747672_[MS-LED]访问域名实际落到服务器端被访问了4次，但是去访问IP 就正常，落到服务器端为1次

问题描述：

==========

在启用CDN后，使用域名访问，会在服务其中看到4条日志记录。如果使用IP地址或CNAME进行访问，则是正常的（一条日志记录）。

对于这个问题，能否普及一下azure 中cdn 对于range 回源的原理呢？ 是否有相关文档， 对于我们以前出现过的实际服务器2次访问我能够理解，但是这个4次访问落到实际服务器上， 不清楚是怎么回事儿？难道确认了3次吗？

解决方案：

当开启range回源时，cdn会先发送一个range0-0的请求来获取文件大小，然后根据文件大小进行分片请求，如果文件较小的话，分片的数量会相对较少，请求一个资源的话这样可能会出现多个记录。

==============================

SR_2019091150684_[S500]CDN预加载疯狂地向源站发送请求，已影响源站的正常服务

有关Range回源的说明：

===============

Range 是 HTTP 请求头，用于文件指定部分的请求。如：Range: bytes = 0-999 就是请求该文件的前1000个字节。开启 Range 回源配置能够有效提高大文件分发效率，提升响应速度。

源站需要支持 Range 请求，否则会导致回源失败。

开启 Range 回源配置后，资源在节点上分片缓存，但所有分片的缓存过期时间保持一致，按照用户指定的缓存过期规则。

此功能暂时不支持用户自助配置，需要通过Azure CDN产品组进行配置。

SR_2019082848059_[S500]CDN无法缓存内容且向源地址发送重复请求

如果当前一个文件，在未击中CDN缓存的情况下，为什么会进行4次回源的访问。

默认开启了range回源功能，这时CDN节点会使用range0-0先请求一次源站来获取资源长度，随后按照一定的range范围进行分段请求，因此会出现客户端一次请求产生多次回源记录的现象，如果不需要的话，我们可以后端关闭range回源功能，如果源站的文件较小的话，这个不会有太大影响，如果文件较大的话，可能会影响回源成功率和回源带宽；

==========================

SR_2020071640119_[MS-LED]访问CDN加速域名时报错：This application has no explicit mapping for /error, so you are seeing this as a fallback.

关于range回源，请参考以下信息：

==================================================

当开启Range回源时，有用户请求来时，CDN理论上会先发一个请求到源站来判断文件大小，这个请求可能在文件本身请求比较小的时候产生一些消耗，所以可能会导致小文件的请求相对慢一些。

一般Range回源是针对大文件的，如果域名下的大文件（比如100M以上）比较多，开启range回源可以减少回源并发和回源率，也可以提升性能。但是域名下如果小文件占比比较多，就不建议开启。

Update 2020.07.27：

Range回源利弊【By CDN 产品组】：Range回源主要的好处是对于大文件可以减少回源带宽/流量、增加命中率。但如果源站对range请求不支持的话，存在出错的风险。另外，如果开启了range回源，第一次都会有一个0-0探测，会轻微增加源站的请求次数，这样对于小文件来说，增加了额外的开销而并没有产生太多的好处，所以不建议对小文件打开range回源。
