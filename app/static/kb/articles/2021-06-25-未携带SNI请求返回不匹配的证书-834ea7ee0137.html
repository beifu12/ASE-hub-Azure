SNI 的作用

使用下面的配置，不论浏览器请求哪个主机，都只会收到默认主机www.example.com的证书。这是由SSL协议本身的行为引起的——先建立SSL连接，再发送HTTP请求，所以nginx建立SSL连接时不知道所请求主机的名字，因此，它只会返回默认主机的证书。

server {

listen          443;

server_name     www.example.com;

ssl             on;

ssl_certificate www.example.com.crt;

}

server_name     www.example.cn;

ssl_certificate www.example.cn.crt;

1.问题描述

客户应用程序网关配置多个mutisite listener， 且所有HTTPS listener都启用Require Server Name Indication，按照官方文档，当客户端请求未指定 SNI 标头，并且所有多站点标头都启用了需要 SNI时，应用程序网关应该返回配置的第一个 HTTPS 侦听器的证书（按顺序），但测试发现最终用户的AppGW没有返回第一个listener上的证书

根据网关对是否携带SNI的访问说明：https://docs.azure.cn/zh-cn/application-gateway/ssl-overview

没有SNI的情况下，并且所有Listener都启用了SNI True（您的两个网关所有HTTPS listener都启用了SNI True设置），所以返回配置的第一个 HTTPS 侦听器的证书（按顺序）

通过第三方工具检测https://www.ssllabs.com/ssltest/ multimediaows.3m.com.cn

也可以通过linux 检测

openssl s_client -showcerts -connect 40.73.122.83:443

AppGW的listener配置，第一个listener及其cert的配置为：

"HttpListeners": [

{

"FrontendIP": "WAF-Pr-feip",

"FrontendPort": "WAF-Pr-feport-HTTPS",

"HostName": "ftdvhealthcheck.3m.com.cn",

"Name": "ftdvhealthcheck_Listener_Secure",

"Protocol": "Https",

"RequireServerNameIndication": "True",

"SslCert": "wildcard.3m.com.cn.2021.pfx"

},

2. 带SNI获取该listener的证书，可以看到该listener的证书对应CN =*.3m.com.cn

CMD: openssl s_client -connect ftdvhealthcheck.3m.com.cn:443 -servername ftdvhealthcheck.3m.com.cn

3. 测试不带SNI访问该AppGW, 可以看到返回的是另一个listener的证书 CN = *.3mdigital.cn

CMD: openssl s_client -connect ftdvhealthcheck.3m.com.cn:443

*40.73.122.83 is the VIP of application gateway

后台查看第一个HTTPS对应的Rule为：3mdigital_Rule_Secure， 因此请求未带SNI时返回了该Rule对应Listener

后台看到的rule的顺序为：

(3mdigital_Listener_Secure)上的证书：3mdigital.cn.pfx

也就是说请求未指定 SNI 标头，AppGW返回的是第一个HTTPS协议 Rule的对应listener上绑定的证书。

原因分析：经后线产品组确认，当客户端请求未指定 SNI 标头，并且所有多站点标头都启用了需要 SNI时，应用程序网关应该返回配置的第一个 HTTPS 侦听器的证书（按顺序），这里的顺序是按照AppGW上配置的Rule的顺序来确定的。也就是说请求未指定 SNI 标头，AppGW返回的是第一个HTTPS协议 Rule的对应listener上绑定的证书。

解决方案：提供上述产品组的对AppGW行为的描述，建议最终用户根据产品设计的行为来规划AppGW rule的顺序。
