背景： 客户的某台Linux虚拟机A因意外修改了某些配置文件如ssh配置文件/etc/ssh/sshd_config导致无法登录了，客户又觉得联系我们从console修复太麻烦，就会想到将此虚拟机操作系统磁盘挂载到正常运行虚拟机B上进行修复。

这里我们有一个已知问题就是，相同版本系统磁盘的UUID是一样的，直接挂载会报错，我们的解决方法就是手动修改下原虚拟机磁盘A的UUID。如下方所示：

[host-24-61-56-74 vda1]# uuidgen

5dee2a7e-cae0-4807-8943-e13ca532dd53

[host-24-61-56-74 vda1]# tune2fs /dev/vdb1 -U 5dee2a7e-cae0-4807-8943-e13ca532dd53

tune2fs 1.42.9 (28-Dec-2013)

但是最近发现如果是在Centos 7系统（默认OS disk文件系统为xfs）上上面这个命令就不好用了，会有如下报错：

[root@leocentos75 sharefile]# uuidgen

093463fa-10c4-4aae-9fac-cad73083cf6d

[root@leocentos75 sharefile]# tune2fs /dev/sdc2 -U 093463fa-10c4-4aae-9fac-cad73083cf6d

tune2fs: Bad magic number in super-block while trying to open /dev/sdc2

Couldn't find valid filesystem superblock.

那么问题来了，是不是CentOS7系统（说成xfs文件系统更确切）不支持修改UUID呢？通过测试发现，如果文件系统为xfs的话，需要使用xfs_admin进行调整的，如下方所示：

7114e890-8c95-414b-ad65-f3b2d42607e9

[root@leocentos75 sharefile]# xfs_admin -U 7114e890-8c95-414b-ad65-f3b2d42607e9 /dev/sdc2

Clearing log and setting UUID

writing all SBs

new UUID = 7114e890-8c95-414b-ad65-f3b2d42607e9

以上方式修改UUID失败，又想mount磁盘拷贝数据时，可参考以下方案。

Linux虚拟机在挂载磁盘修复问题时有时会出现mount失败的问题会提示有superblock的问题不让挂载，如下所示：

[root@ruite03 ~]# mount   /dev/sdc2  /tmp/ruite02/

mount: wrong fs type, bad option, bad superblock on /dev/sdc2,

missing codepage or helper program, or other error

In some cases useful info is found in syslog - try

dmesg | tail or so.

此问题很可能是由于UUID重复导致，这时通常会建议客户修改UUID再进行挂载，但是当磁盘为OS磁盘且文件系统内部本身存在一些问题时是无法修改UUID的，如下所示：

[root@ruite03 ~]# xfs_admin  -U  14465584-7f2b-4c22-a1c0-4d4869bb5b63    /dev/sdc2

ERROR: The filesystem has valuable metadata changes in a log which needs to

be replayed.  Mount the filesystem to replay the log, and unmount it before

re-running xfs_admin.  If you are unable to mount the filesystem, then use

the xfs_repair -L option to destroy the log and attempt a repair.

Note that destroying the log may cause corruption -- please attempt a mount

of the filesystem before doing this.

此时只需要使用mount -o nouuid /dev/xxxx /xxxx 挂载即可
