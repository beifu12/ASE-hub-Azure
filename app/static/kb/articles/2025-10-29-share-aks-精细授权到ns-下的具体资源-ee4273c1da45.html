前提：

认证和授权是两码事，这个概念要明确。

认证是识别用户身份，用户登录azure ，输入账号密码，azure确认用户身份。

授权是确认身份后，系统或者程序决定这个用户可以执行哪些权限。

参考文档：

参考文档 ： https://docs.azure.cn/zh-cn/aks/azure-ad-rbac?tabs=portal

K8s 官方文档：  Using RBAC Authorization | Kubernetes

认证部分：

用户必须在azure 级别 授予“Azure Kubernetes 服务 RBAC 读取者” 角色，用户才能获得 aks config 文件的权限。

K8s 借助 config 文件识别用户身份。

授权部分：

定义一个role ， 将azure ad 的用户/ 组 绑定这个role.

以下示例是分配用户查看 ns default 下 deployment 的权限

借助k8s 自身的role 、rolebingding ; 进行授权。

Role ymal 定义了 名字叫deployment-reader 的 role 可以在什么范围下 对什么样的对象执行什么样的权限

Role.yaml

apiVersion: rbac.authorization.k8s.io/v1

kind: Role

metadata:

namespace: default

name: deployment-reader

rules:

  • apiGroups: ["app"]     # "" indicates the core API group

resources: ["deployments"]

verbs: ["get", "watch", "list"]

Rolebingding yaml 将了 一个叫deployment-reader-rolebind 的 rolebinding 定义了哪个用户具有上面的deployment-reader 角色 。

e4488e2b-b066-4372-8b7a-9697cb28014 这个是用户的对象id ，也可以是upn.

Rolebinding yaml

This role binding allows "user" to read pods in the "default" namespace.

You need to already have a Role named "deployment-reader" in that namespace.

kind: RoleBinding

name: deployment-reader-rolebind

subjects:

You can specify more than one "subject"

  • kind: User

name: e4488e2b-b066-4372-8b7a-9697cb28014b    #userObjectId，也可以是用户的upn

roleRef:

"roleRef" specifies the binding to a Role / ClusterRole

kind: Role #this must be Role or ClusterRole

name: deployment-reader # this must match the name of the Role or ClusterRole you wish to bind to

apiGroup: rbac.authorization.k8s.io
