Additional Notes

This document provides an overview of the current backup and throughput performance for SAP HANA workloads using Azure Backup. It includes debugging steps for performance issues and methodologies for diagnosing and resolving them.

To understand the current backup and throughput performance that Azure Backup provides for SAP HANA workloads, refer to the following articles:

Limiting Backup Throughput Performance

To begin debugging performance issues:

Determine the impact level of the performance issue:

Is it limited to the Azure region where the HANA VM is hosted?

Does it affect all HANA VMs in the subscription or just one?

Query to Check Impact Level

Firstly, Check the level of impact of the performance issue, is it restricted to:

The Azure region in which the customer has their HANA VM

The Subscription of which the HANA VM is a part – is it impacting all the HANA VMs in the subscription or is it just a single VM?

To find the above use the following Kusto query:

union cluster('mabprod1').database('MABKustoProd1').WBEBackupStats,

cluster('mabprodwus').database('MABKustoProd').WBEBackupStats,

cluster('mabprodweu').database('MABKustoProd').WBEBackupStats

| where SubscriptionId !in (GetInternalSubscriptions())

| where DeploymentName contains "we"

| where DatasourceType contains "hana"

| where BackupType contains "full"

| extend DatasourceSizeInGB = todouble(DataTransferred) /(1024 * 1024 * 1024)

| extend ReadThroughputInMBps = parse_json(Properties).OverallReadThroughputInMBps

| extend WriteThroughputInMBps = parse_json(Properties).OverallWriteThroughputInMBps

| extend BackupSpeedAchievedIncludingExtensionDelaysInMbps = (todouble(DataTransferred)/(todouble(DurationInMS)/1000)/(1024 * 1024))

| where DatasourceSizeInGB > 50

| where TIMESTAMP > ago(5d)

| where ErrorCode contains "success"

| extend countBruUnits = tolong(parse_json(Properties).CountOfBRUUnits),

countBRUReplicas = tolong(parse_json(Properties).CountOfBRUReplicas)

| extend ExpectedMaxBackupSpeedWithoutCap = countBRUReplicas*(countBruUnits/2)

| extend ExpectedMaxBackupSpeed = iff(ExpectedMaxBackupSpeedWithoutCap > 450, 450, ExpectedMaxBackupSpeedWithoutCap)

| project TIMESTAMP, DeploymentName, ExpectedMaxBackupSpeed, ReadThroughputInMBps, WriteThroughputInMBps, BackupSpeedAchievedIncludingExtensionDelaysInMbps, DatasourceSizeInGB, DurationInMS, ContainerName, DatasourceName, BackupType, ErrorCode, PitId, TaskId, DataTransferred, DatasourceId, SubscriptionId, Level, Properties

If all the machines from that region are affected, please create an IcM with all these details. Based on the number of VMs within the subscription that are affected the most probable cause for performance issue may vary. Generally, if multiple VMs are affected it could be a network issue. However, to zero-in on the right cause, follow these steps:

Approach 2

Full/Differential/Incremental backups for the database uses the same storage account while log may use a different storage account based on storage account availability.

Plugin calls the protection service API to get the SAS URI for the storage accounts. The call to the protection service is made every 24-36 hours, i.e. once a call to protection service is made it is cached in the plugin service for a day.

In order to get the storage account used for a particular database backup type (Full/Diff/Incr or log), get all the jobs that are triggered in the last 48 hours and use the below Kusto query:

let taskids = WBEBackupStatsAll

| where DatasourceId == "<DsId>"

| where BackupType == "<BackupType>"

| summarize by TaskId, BackupType;

WBETraceLogAll

| where TIMESTAMP > ago(10d)

| where DeploymentName == "<geo>-pod01"

| where ServiceName == "tel"

| where TaskId in (taskids)

| where Message == "[HANAPlugin Bkp]: Stamping PIT metadata."

| extend BkpType = iif(Properties contains "FULL_SCHD","Full","Log")

When the VM is in region X, and the vault is also in the same region X, the storage calls are routed within the internal network (faster response) to the storage account. Hence, when we check the perf logs on the storage account, there is a clientip column, which indicates the IP address of the client (in this case, the SAP VM). If the client IP is of IPV4 (For e.g. ClientIP=63.97.36.15:24637), then it means that its not hitting it directly internally within the network, but routing it outside the datacenter, on to the public internet, and then coming back into the data center. This increases the latency, since it adds hops on the path, and some path can be slower. If the client ip is IPV6 (for e.g ClientIP=fd00::556d:7020:d00:ae8:449d]:49798), then its within the datacenter network, and should be fast and the performance should be better.
