---------------------Second Issue---------------------

We have these domains:

www.safespec.dupont.com - 152.199.39.108 (origin site)

www.safespec.dupont.cn - 157.185.178.148 (China domain)

During the 13th and 14th weekend, users in China started to experience HTTP 504 error accessing www.safespec.dupont.cn. No changes were made whatsoever and website was working fine the day before.

Analysis:

China CDN team was able to fix the issue by changing the China's CDN provider.

Keep in mind that we are doing CDN chaining here between China CDN and Verizon's CDN.

Changing the China's CDN provider fixed the issue because the previous one was doing validation of the website www.safespec.dupont.cn against the origin site IP which is the Verizon CDN 152.199.39.108. This is producing a certificate error, as show here:

The command shows a random certificate returned which causes the error.

You can see we are connecting to www.safespec.dupont.cn but we are not using its original IP to connect. Instead, we are using the origin site IP 152.199.39.108, which belongs to Verizon.

This is the exact same validation that previous China CDN provider was doing. New China CDN provider that was changed is not doing this validation, hence the problem is no longer happening.

Next question is why Verizon is not displaying the right certificate on this specific scenario?

Well, Verizon uses a shared SNI model as I have explained before. This means, among other things,  that if Verizon's POP is not aware of a certificate that we request, it would return a random one.

In this case, we are requesting Verizon's POP for the certificate of www.safespec.dupont.cn, but it is not aware of it, so it returns a random one, only for the particular scenario of connecting to www.safespec.dupont.cn via Verizon's IP.

This scenario won't happen under normal circumstances because DNS is not resolving Verizon's IP (152.199.39.108) for domain www.safespec.dupont.cn. This was only happening for the previous China CDN provider validation.

What can we do to prevent this?

You can see the circumstance that led to this issue were completely unrelated to changes or actions that we have performed from both Microsoft or the customer side.

This issue was caused by the interoperability of the CDN providers that are involved.

Previous China CDN provider performing a particular validation of domain through origin site's IP. Which is not the case for the new China CDN provider.

The shared SNI model used by Verizon, which is not common across other CDN providers such as Akamai or Microsoft itself.

These are both peculiarities among CDN providers that we cannot unfortunately regulate or change but to learn and be aware of this so that these behaviors become known in the future and then immediate actions can be taken without any long diagnosis.

As per Verizon's recommendation we also enabled HTTPS for www.safespec.dupont.cn so that validations will not show the wrong certificate. Verizon incident: INC1105746.
