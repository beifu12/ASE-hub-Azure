Section 3: Error

Unable to Register ASR RCM Appliance with Private Endpoint Enabled RSV failing with error “ Private zone 'privatelink.vaultcore.azure.net ' is already linked”

Symptoms:

Private zone 'privatelink.vaultcore.azure.net ' is already linked. or Private zone ‘privatelink.prod.migration.windowsazure.com ' is already linked.

Section 4: Reason for failure and Remediation steps

Private DNS Zone for Azure Key Vault is already linked to the Virtual Network on which Recovery Services Vault Private Endpoints are configured to.

We can also fall into this issue if you create discovery endpoint DNS Zone and link it to RSV PE VNET prior to RCM Appliance Registration, so it is better you don’t create the discovery endpoint prior ahead and instead when you do RCM Appliance registration, it will automatically create and link it accordingly.

Synopsis of issue:

Please read synopsis of issue below on how to validate and assess the impact which can help customers to plan this step accordingly.

When you create the RSV with PE for ASR, it will create endpoints for Site Recovery related Microservices and link required DNS Zone which is in our/user control. Then you try to add and register an RCM Appliance to the vault, and it requires 2 additional Endpoints which are created for Key Vault and Discovery which are not under our control. These 2 Endpoint will have its own IP Address reserved from PE Subnet, and then it needs Private DNS Zone to resolve those IPs to do that it will try linking to the Vnet.

'privatelink.vaultcore.azure.net ' >> For Key Vault

Private zone ‘privatelink.prod.migration.windowsazure.com  for Discovery Endpoint The moment you initiate RCM Appliance Registration from App configuration page, it will invoke a deployment which you can monitor from RSV Residing Resource Group as shown below and first deployment should be the Azure Key Vault creation as part of ASR Appliance requirement and it will then create Private Endpoints, followed by Private DNS Zone, followed by DNS Zone Link job.

In this case, I have set up the lab with Private DNS Zone for the Key Vault and linked to the Virtual Network where my Recovery services PE is residing.

Since I have this endpoint already linked, this will end up in conflict and then lead to failure as shown below.

To fix the issue, I need to break the link and to do that first validate from Private DNS Zone Overview page to see how many IP’s and Key vaults are associated with this DNS Zone which are likely to be impacted as DNS will not resolve the listed IP’s the moment we unlink, inform customers, and proceed with unlinking as per their convenience. In the below snippet, you don’t find any IP or Key Vault associated with DNS Zone because I don’t have any already, so there will be no impact, but in customer case it may or may not have entries possibly based on their environment.

To unlink, you need to go to the Private DNS Zone in question -> Virtual Network Links -> Validate if it’s linked with Vnet residing RSV PE -> Delete it(it takes couple of minutes) and then Initiate the Registration which will link the Private DNS Zone back with RSV PE Vnet, which should barely take less than 10 minutes, though this impact is for small window, it is better to inform customer so that they can plan accordingly.

Once I deleted and invoked the Registration again, it completed within less than 10 minutes to link DNS Zone back which can be monitor from deployments section as suggested earlier.

Resolution:

You need to Un-link the DNS Zone via Azure Portal -> Private DNS Zones -> DNS Zone in question should be privatelink.vaultcore.azure.net  or ‘privatelink.prod.migration.windowsazure.com ' based on error message -> Virtual Network Links -> Delete the link associated with Vnet in question associated with Recovery services vault.
