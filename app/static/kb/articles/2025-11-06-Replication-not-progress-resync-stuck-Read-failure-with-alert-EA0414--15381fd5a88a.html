Exact reason for failure

Disk not readable - hardware issue

(OR)

Azure VM disk resize case: There is another case for re-protect protection from Azure to on-premises. Here Azure VM disk resize done after enabled the re-protect. As Azure VM disk resize done by user, after resizing done, the disk resynchronization starts automatically because of auto resync. As the re-sync progress got stuck here because old size of disk last offset read got failed here due to Azure VM disk resize. Here Azure VM got resized, but attached on-prem disk to new stack appliance has old size.

The customer have Storage Replica feature installed in the servers, SR (storage replica) might adversely affect the ability of other things to access the disks/volumes

The resolution is to uninstall the storage replica feature from the server and restart server.

Recommended action to resolve the issue

For disk hardware issue case need to follow below actions:

Check whether the reported offset is readable for said offset and length using

External tool(HexEditor) and if it fails then check with disk vendor for further assistance

(or)

Run the util to check if the offset is readable or not

a. Download DiskReaderTests.exe file attachment from

b. Extract the zip file and copy DiskReaderTests.exe to local directory on agent.

c. Open command prompt in admin mode, run the below command by replacing the appropriate values and collect the results.

<localdir>:\DiskReaderTests.exe <disk-index> <offset> <lengthInBytes>

Please verify same with dd command for same offset with below command:

time dd if=/dev/sda of=/dev/null bs=4194304 count=1 skip=<offset to check/4194304>

For example to verify read at offset 0,

time dd if=/dev/sda of=/dev/null bs=4194304 count=1 skip=0

For example to verify read at offset 1424545021952,

time dd if=/dev/sda of=/dev/null bs=4194304 count=1 skip=339638

If dd also give same error code 5 then please check with disk vendor for further assistance

For Azure VM disk resize case need to follow below actions to unblock re-protect failback:

Incident 393502746 : [Waiting on CSS]Failback Azure to onpremises [Sd 2305250030000897 Cx ashghal.gov.qa ][SE-anrod][reprotection cannot be perform VM keeps critical]

Work around steps for Example Azure VM ARCHSRVCFG01:

Extend the VMDKs on the ASR appliance:

a. Login to vCenter.

b. Go to Appliance.

c. Identify the disks to be extended -> You can check the same Vcenter->on-prem ASR appliance machine->Edit settings->search for the attached disk [DS_SCADA01] ARCHSRVCFG01/ARCHSRVCFG01_1.vmdk

d. Modify the disk size to same as Azure VM disk size. which in this case would 4TB. Cross verify from the Azure VM disk size from portal.

After extending the disk size on the appliance, resync will be performed automatically. Monitor it for some time(in my case it was 45mins). If in case you observe that resync is not taking place automatically, then perform the re-synchronization from the Portal > you will observe the resync banner under Vault-> replicated items.

While resynchronization is going on, you can do below step any time. Go to vCenter -> on-prem Source machine -> Edit settings -> Detach the disk(vmdk which was modified in step one of appliance) -> Make sure DO NOT SELECT OPTION(Delete from datastore) -> click OK -> Again go to Edit settings->Add new device-> add existing Hard disk ->Click Ok (This will Attach the VMDK([DS_SCADA01] ARCHSRVCFG01/ARCHSRVCFG01_1.vmdk) on the on-prem Source VM.

This will reflect the new size on the On-Prem VM.

Monitor the replication depending on size it will take its own time and replication should go to healthy state.

Once healthy you are good to perform Planned failover (Failback).
