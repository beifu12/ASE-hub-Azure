问题描述：

客户的ER可以看到地端传过来的路由，但是vhub里看不到同样的路由

Vhub:

排查思路：

除了在dumprouting来查看ER的BGP路由，也可以使用另一种方式来查看客户的ER BGP路由，这种方式可以看到客户的ASN，而dumprouting无法看到：

首先在ASC上如下图位置获取到用户的VRF ID

然后到javirs actions中输入如下图指令：

sh ip bgp vpnv4 vrf 'VRF ID'

这个时候就可以看到客户的带ASN的路由情况

之后查看客户vhub路由，发现显然问题不是由ASN引起的：

这时候就需要BGP日志来进一步排查了:

Kusto Gateway BGP log:

cluster('aznwchinamc.chinanorth2').database('aznwmds').GatewayTenantLogsTable

|where GatewayId == 'a506004a-7622-4878-8a45-de800045d74f'

|where TIMESTAMP > datetime('2025-09-12 02:00:00') and TIMESTAMP < datetime('2025-9-12 06:00:00')

|where Message contains "<BGP>"

|project PreciseTimeStamp , RoleInstance , Message

Gateway ID需要从ER gateway的child gateway来获取

Kusto Vhub BGP log:

cluster('aznwchinamc.chinanorth2').database('aznwmds').RouteServiceBgpLogsTable

| where Tenant contains "armrg-1a114619-03aa-4acd-b2a5-48db24170052"         //armrg-RouteService Id

| where TIMESTAMP > datetime('2025-09-12 02:00:16') and TIMESTAMP <  datetime('2025-09-12 06:45:16')

| where Message contains "<BGP>"

| project TIMESTAMP, RoleInstance, Message

Route id需要从vhub里获取

通过dumprouting可以看到该路由建立了2天22h

调整日志时间到路由开始传播的时间点发现如下log:

日志表示该路由是因为community 65517：65517被drop的

这个是azure by design的行为，该问题是route server/vhub向地端传播路由时会添加这个community，然后如果是VPN gateway会把这个community移除，所以不会产生任何问题。

但是express route gateway 并不会移除这个community，所以当客户把这个路由从地端传回azure时，express route gateaay 会检测MSEE传播过来的这个community并drop该路由。

问题本质是azure防止路由回环的设计，如果客户一定需要这样配置，只需要由客户地端删除该community即可

删除后可以看到路由已经被vhub正常学到：
