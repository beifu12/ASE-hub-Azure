2022/12/20

参考工单：SR_20220929191386_Excessive packet loss when using Azure VPN Gateway

问题现象：

客户的拓扑结构如下，客户在中国和新加坡Azure之间通过Azure VPN gateway建立了Ipsec VPN 隧道

China Azure VPN gateway地址：10.93.31.6

Singapore Azure VPN Gatewya地址：10.94.31.6

两个VPN Gateway之间是通过客户的底层ECR网络打通的，不是通过Internet。 数据包先到达BJ ECR ，再到达BJ POP，再到达SG POP，再到达SGECR，最后到达SG VNG

客户ECR 和POP之间的MTU是1359

客户的问题现象是China VM和SG VM之间传输大包的时候无法正常传输，比如ping包size是1266 Byte时可以ping通，ping包size是1267 byte时就ping不通

问题分析：

通过在 China Azure VM， China Azure VPN gateway，China ECR， BJ POP，SG POP，SG ECR， SG Azure VPN Gateway，SG Azure VM抓包可以发现，China 和SG 的VPN Gateway在发送封装好的ESP包的时候，IP ID字段均为0000， 当ESP包较大时，经过ECR网络会被分片，到达对端VPN gateway后，由于缺少IP ID字段，分片后的ESP包无法重组，导致分片的包被VPN gateway 丢弃，所以造成大包无法正常传输的问题

解决方案：

PG在两端的网关上部署了Fix，修复了网关ESP包IP ID为0000的问题，这样ESP包在分片后就可以重新组装。

但是目前不确定该Fix所有网关都部署了，如果大家遇到类似MTU小于1500的网络时，可以抓包自行确认一下网关的ESP包的IP ID字段的值

如果是0000，升级到PG进行修复
