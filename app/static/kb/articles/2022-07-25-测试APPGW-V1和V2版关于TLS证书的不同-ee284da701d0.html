一句话摘要

V1和V2版的Azure Application Gateway, 前端配置为80访问，后端配置为443方式，后端池为客户APPGW后面的VM。测试结果为V1版的网关后端探测可以成功，V2版的网关不管是在httpsettings中选择“”使用知名的CA证书“，还是选择上传客户端证书中提取出来的根证书，V2版后端探测状态始终显示为失败的状态。

问题现象 / 场景

  • V1和V2版的Azure Application Gateway, 前端配置为80访问，后端配置为443方式，后端池为客户APPGW后面的VM。测试结果为V1版的网关后端探测可以成功，V2版的网关不管是在httpsettings中选择“”使用知名的CA证书“，还是选择上传客户端证书中提取出来的根证书，V2版后端探测状态始终显示为失败的状态。
  • 需要注意的是，APPGW前端上传的PFX格式证书，也是需要带有证书中间件的证书。否则Linux客户端或其他不能自动下载证书中间链的客户端将无法正常访问Web服务。
  • 最终客户使用如下方法将中间链证书导出后，将中间链证书追加到Server端的公钥证书中，解决了V2版网关通过Https方式探测后端Server失败的问题。

V1和V2版的Azure Application Gateway, 前端配置为80访问，后端配置为443方式，后端池为客户APPGW后面的VM。测试结果为V1版的网关后端探测可以成功，V2版的网关不管是在httpsettings中选择“”使用知名的CA证书“，还是选择上传客户端证书中提取出来的根证书，V2版后端探测状态始终显示为失败的状态。

测试：

========

创建一台Linux VM (Centos)，通过在host文件中指定域名对应的IP为客户APPGW后面的VM IP 40.73.127.74:

发现通过Linux客户端是无法正常访问贵方的域名的，报错“Unable to locally verify the issuer’s authority” 或“Peer’s Certificate issuer is not recognized.”说明客户的Server中Web应用使用的证书是不包含完整证书链的：

查看该Linux下的/etc/pki/tls/certs/ca-bundle.crt文件，发现Linux系统中授信的证书list中并没有贵方证书的签发证书，即贵方证书链中的中间件证书：

v

在windows系统下导出贵方证书的中间链证书，导出方法如下：

https://docs.microsoft.com/zh-cn/azure/application-gateway/certificates-for-backend-authentication

在Linux下使用如下命令将该中间件证书添加至授信的证书list

cat customermedia.cer >> /etc/pki/tls/certs/ca-bundle.crt #ubuntu 是: /etc/ssl/certs/ca-certificates.crt, centos是/etc/pki/tls/certs/ca-bundle.crt

发现该Linux VM可以成功访问到贵方APPGW后面的VM IP 40.73.127.74上的Web服务：

排查结论：

==========================

根据如上测试，我们可以看到,  V1版的APPGW证书机制会自动下载中间链证书，所以V1版的APPGW可以正常和客户的VM建立SSL握手。V2版的网关不会自动下载中间链证书，导致APPGW无法和Server端进行正常的证书验证。

此种情况建议客户向证书颁发机构申请带有完整证书链的证书，在APPGW V2的后端server端上传带有完整证书链的证书。

需要注意的是，APPGW前端上传的PFX格式证书，也是需要带有证书中间件的证书。否则Linux客户端或其他不能自动下载证书中间链的客户端将无法正常访问Web服务。

最终客户使用如下方法将中间链证书导出后，将中间链证书追加到Server端的公钥证书中，解决了V2版网关通过Https方式探测后端Server失败的问题。

方法如下：

5.将导出的证书上传到Linux Server中，使用如下命令将该中间链证书追加到Server的公钥.crt证书中，重启nginx服务后，APPGW的后端探测就正常了。

#cat customermedia.cer >> sslserver.crt
