Hi larry,

由于问题紧密关联到开源项目--Linux虚拟机，我们收集到若干关于net.ipv4.tcp_tw_的文章，这些文章都倾向于默认关闭net.ipv4.tcp_tw_recycle。为您提供以下几篇文章参考：

Coping with the TCP TIME-WAIT state on busy Linux servers中阐述：Enabling this option is not recommended since this causes problems when working with NAT (Network Address Translation).

tcp_tw_recycle和tcp_timestamps导致connect失败问题 中阐述：tcp_tw_recycle – BOOLEAN Enable fast recycling TIME-WAIT sockets. Default value is 0. It should not be changed without advice/request of technical experts.

tcp_tw_recycle参数引发的故障 中阐述：在一些高并发的 WebServer上，为了端口能够快速回收，打开了 tcp_tw_reccycle ，而在关闭 tcp_tw_reccycle 的时候，kernal 是不会检查对端机器的包的时间戳的；打开了 tcp_tw_reccycle 了，就会检查时间戳，很不幸移动的cmwap发来的包的时间戳是乱跳的，所以我方的就把带了“倒退”的时间戳的包当作是“recycle的tw连接重传数据，不是新的请求”，于是丢掉不回包，造成大量丢包。

我们针对Azure上的部分Linux虚拟机进行了测试，SLB Probe会被net.ipv4.tcp_tw_recycle ==1干预的虚拟机包括：

Centos 6.7   2.6.32-573.22.1.el6.x86_64

Centos 7.2   3.10.0-327.10.1.el7.x86_64

以下版本虚拟机暂时没有复现问题：

Centos  6.5    2.6.32-431.29.2.el6.x86_64

Centos  6.6    2.6.32-504.30.3.el6.x86_64

Centos 7.0   3.10.0-123.20.1.el7.x86_64

Centos 7.1   3.10.0-229.20.1.el7.x86_64

这也说明net.ipv4.tcp_tw_recycle 并非唯一决定因素，内核版本也会影响测试结果。

最后，我们建议您使用Azure的虚拟机时，net.ipv4.tcp_tw_recycle=0，避免不可预测的问题。

如何查看recycle参数：您帮忙在虚拟机里执行以下 s  查看一下返回的参数是1还是0？

示例：

解决方式：

1.临时修改kernel参数，及时生效，重启系统后无效

[root@hlmvme683 ~]# echo 0 > /proc/sys/net/ipv4/tcp_tw_recycle

[root@hlmvme683 ~]# cat /proc/sys/net/ipv4/tcp_tw_recycle

0

2. 为了避免重启后无效，需要将相应的参数设定保存到/etc/sysctl.conf，重启VM或者执行sysctl –p 生效

[root@hlmvme683 ~]# echo 'net.ipv4.tcp_tw_recycle = 0' >> /etc/sysctl.conf

[root@hlmvme683 ~]# sysctl -p

net.ipv4.ip_forward = 0

net.ipv4.conf.default.rp_filter = 1

net.ipv4.conf.default.accept_source_route = 0

kernel.sysrq = 0

kernel.core_uses_pid = 1

net.ipv4.tcp_syncookies = 1

kernel.msgmnb = 65536

kernel.msgmax = 65536

kernel.shmmax = 68719476736

kernel.shmall = 42949672= 0
